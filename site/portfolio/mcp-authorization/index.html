MCP authorization server (demo)

Python 3.13 · MCP over Streamable HTTP · FastAPI · PyJWT · PostgreSQL · Keycloak 26.7.1 · Docker Compose

What this project shows

  • An external authorization server, Keycloak, with the MCP server as a strict resource server. Every token is validated in the server's own code (signature, issuer, expiry, audience) against the published key set, and every failure closes.
  • A token is a ceiling on what an application may do, never a statement of what the person may do. Three coarse scopes meet roles the server resolves per request, and every call is decided by the intersection.
  • The shape of a refusal follows its remedy. A tool the token cannot reach is absent from the listing, scope without the role is a protocol error, and a segregation-of-duties breach is a domain rejection.
  • The authorization layer is portable: the purchase-to-pay domain can be deleted without untangling it, and the layer's tests run with the domain deleted.

An MCP server where authorization is the subject

An MCP server over a mock purchase-to-pay ERP. Two callers ask the same endpoint the same question and get different answers. A tool a caller may not reach is absent rather than refused. docs/walkthrough.md follows one from the login screen onward, every wire exchange copied from a capture a test checks it against. What this cost counts fifty-one commits of documentation before the first line of Python, and what running code did to that design.

Keycloak is the authorization server, and a client it provisions from a hosted metadata document inherits no PKCE pin. It arrives accepting plain while every authored client in the realm pins S256. The obvious repair is inert, because a profile is only as reachable as its policy's condition, and conditions are per-event. keycloak/README.md has both, checked against Keycloak 26.7.1.
